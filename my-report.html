The PostgreSQL receiver already has db.server.query_sample (disabled by default) querying pg_stat_activity and already captures wait_event and wait_event_type. However there is zero blocking detection today — no blocker PID, no lock info, no idle blocker fetch. Unlike SQL Server (which needs a second query) and Oracle (which uses COALESCE(SQL_ID, PREV_SQL_ID)), PostgreSQL exposes idle sessions directly in pg_stat_activity and has the built-in pg_blocking_pids(pid) function (v9.6+), making a single enhanced query sufficient.

Proposed New Attributes (7)

Attribute Type Source Description
postgresql.blocking_pid int pg_blocking_pids(pid)[1] PID of the immediate blocker. 0 when not blocked. Stripped for non-blocked sessions.
postgresql.blocking_pids string pg_blocking_pids(pid) Comma-separated list of all blocking PIDs. PostgreSQL can have multiple concurrent blockers (unlike SQL Server / Oracle).
postgresql.blocking.start_time string pg_stat_activity.state_change RFC3339 UTC timestamp of when the blocking wait began (when session entered current wait state).
postgresql.lock_mode string pg_locks.mode Lock mode being waited on (e.g., ExclusiveLock, RowExclusiveLock, ShareLock).
postgresql.lock_type string pg_locks.locktype Type of locked object: relation, transactionid, tuple, extend, advisory.
postgresql.locked_relation string pg_class.relname via pg_locks.relation Name of the table/relation being locked (e.g., orders). Empty when locktype is not relation-based.
postgresql.transaction_start string pg_stat_activity.xact_start RFC3339 UTC timestamp of when the blocking transaction started. Helps gauge how long a blocker has been holding locks.

Proposed SQL Query

Single enhanced query — replaces the existing querySampleTemplate.tmpl. No second query needed.

SELECT
  sa.pid,
  sa.datname,
  sa.usename,
  sa.application_name,
  sa.client_addr,
  sa.client_port,
  sa.client_hostname,
  sa.query,
  sa.state,
  sa.wait_event_type,
  sa.wait_event,
  sa.query_start,
  sa.state_change,
  sa.xact_start,
  sa.query_id,
  sa.backend_type,
  -- Blocking info (pg_blocking_pids is built-in since PostgreSQL 9.6)
  pg_blocking_pids(sa.pid)           AS blocking_pids,
  (pg_blocking_pids(sa.pid))[1]      AS blocking_pid,
  -- Blocking start time: when session entered current wait state
  CASE WHEN cardinality(pg_blocking_pids(sa.pid)) > 0
       THEN to_char(sa.state_change AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS"Z"')
       ELSE '' END                   AS blocking_start_time,
  -- Lock details for blocked sessions (NOT granted = waiting)
  bl.mode                            AS lock_mode,
  bl.locktype                        AS lock_type,
  COALESCE(c.relname, '')            AS locked_relation,
  -- Blocker's transaction start (how long has blocker held locks)
  CASE WHEN cardinality(pg_blocking_pids(sa.pid)) > 0
       THEN to_char(sa.xact_start AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS"Z"')
       ELSE '' END                   AS transaction_start
FROM pg_stat_activity sa
LEFT JOIN pg_locks bl
  ON  bl.pid = sa.pid
  AND NOT bl.granted
LEFT JOIN pg_class c
  ON  c.oid = bl.relation
WHERE sa.backend_type = 'client backend'
  AND sa.pid != pg_backend_pid()
  AND sa.query IS NOT NULL
  AND sa.query != ''
  AND (
    -- Active sessions
    sa.state = 'active'
    -- Idle sessions that are blocking others (idle in transaction holding locks)
    OR sa.pid IN (
      SELECT unnest(pg_blocking_pids(pid))
      FROM   pg_stat_activity
      WHERE  cardinality(pg_blocking_pids(pid)) > 0
    )
  )
ORDER BY sa.query_start
LIMIT $1

Why no second query?

  • pg_stat_activity already shows ALL backends including idle ones holding open transactions — no separate fetch needed unlike SQL Server.
  • pg_blocking_pids(pid) is a built-in PostgreSQL function (v9.6+) that returns the exact set of blocking PIDs.
  • The OR sa.pid IN (SELECT unnest(pg_blocking_pids(...))) subquery captures idle blockers in the same pass.
